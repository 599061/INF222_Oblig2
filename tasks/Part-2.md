# Checking for type correctness in binary expressions

As *Zerow* uses **nominal typing**,
[measurement units](https://en.wikipedia.org/wiki/Unit_of_measurement) act as types.
Two values are considered _compatible_ if and only if they are equipped with **exactly the same unit**.

This means that binary expressions are only allowed when the left-hand side and right-hand side have identical units.

### Examples

```
declare a equals 4[m] add 8[m] // OK, because both operands have unit `m`, so this expression should typecheck

declare b equals 4[m] add 8[g] // ERROR HERE, because the units `m` and `g` are different, so this must produce a validation error

declared c equals 4[m] add 8[km] // ERROR HERE, because even though both represent distances conceptually, they are different *nominal* units and must therefore not typecheck
```

### What you must validate

For every binary expression (`add`, `sub`, `mul`, `div`):

* Determine the unit of the left-hand side.
* Determine the unit of the right-hand side.
* If the two units are not identical, report a validation error.

You may assume that all referenced variables have a declared unit (either from their declaration or their latest assignment). In this part, you only need to check for equality of unit names. No unit conversions should be performed.

# Checking that variables are not redeclared

In *Zerow*, a variable may only be declared once in a program.

The following program is invalid:

```
declare b equals 3[kg] add 5[kg] 

declare b equals 10[NOK] mul 20[NOK] // ERROR HERE
```
Here, variable `b` is declared twice. This code must produce a validation error that says that `b` has already been declared.

### Your task

When validating variable declarations:
* Keep track of all previously declared variables.
* If a variable name is declared more than once, report a validation error on the second (and any subsequent) declaration.
* Make sure the error message clearly indicates that the variable has already been declared.

# Checking that assignments are only possible to variables that have been declared before

In Part 1, you ensured via cross-references that assignments can only refer to variables that are declared *somewhere* in the program.

However, cross-references in Langium do **not** enforce that the variable must be declared *before* it is assigned to.

The following program should be invalid:


```
assign 4[kg] to b // ERROR HERE: at this point of the program, the variable `b` is not declared yet!

declare b equals 3[kg] add 5[kg] 
```

### Your task

When validating a variable assignment:

* If the variable is declared **after** the assignment statement, report an error.
* If the variable is not declared at all, do **not** report an additional error, because this has already been handled by cross-referencing in Langium.


# Checking that referencing a variable is only possible for variables that have been declared before

Similarly, variables used inside expressions must have been declared earlier in the program.

The following program is invalid:

```
declare b equals 3[kg] add 5[kg]

assign a to b // ERROR HERE: variable `a` exists, but it is referenced before its declaration!

declare a equals 6[kg]
```

### Your task

When validating variable references inside expressions:

* If a variable is declared later in the program, report a validation error.
* If the variable is not declared at all, do **not** report an additional error (this is already handled by Langium cross-references).


# Important implementation notes

## 1. Do not duplicate errors

If a cross-reference already reports an error because a variable does not exist, your validator must not add another error message for the same issue.

## 2. Traversing the AST

The parser generated by Langium produces an **Abstract Syntax Tree (AST)** for each *Zerow* program.

The root node of this tree is:

```
Program
```
From this node, you can traverse subnodes, such as:

* Unit declarations
* Variable declarations
* Variable assignments
* Return statements
* Expressions

Your validation functions should inspect the relevant node types and perform checks accordingly.
